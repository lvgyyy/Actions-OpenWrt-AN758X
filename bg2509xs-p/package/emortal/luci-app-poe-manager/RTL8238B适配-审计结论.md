## 0. 结论摘要与修复状态

前序分析的**寄存器协议部分基本可靠**，端口映射、功率公式、固件选择逻辑都与二进制逐指令对上了。但有三处结论需要更正，代码里有 1 个高危功能风险、1 个中危时序风险和 1 个尚未被代码显式处理的输入级矛盾。

|---|---|---|

| C2 固件两处延时 10ms | 中 | **重新定性为"无需改"**：见下文更正——`rtl-poe.c` 不是原厂代码，ko 与 rtlgsw 两个真机产物均为 ~10ms；代码已补证据注释 |

**最需要优先处理的三件事（审计时判断）：**

1. **`write_bulk` 的固件流格式与厂商不一致**（高危）——原实现每条消息都带 `0xF4` 前缀且块间发 STOP；厂商只第一条带 `0xF4`，后续消息用 `I2C_M_IGNORE_NAK|I2C_M_NOSTART` 续传。原厂 `init.d/rtlgsw` 会 `rmmod rtl8373n`，固件下载完全由用户态承担，所以这条路径**就是**守护进程要走的路。
2. **端口数/端口映射的输入源自相矛盾**（中危）——`pse_src/README.md` 说 7 口（LAN1–LAN7），Web 逆向文档说 8 通道（WAN + LAN2–LAN8）。代码静默选了前者。**已按用户决议保留，待上板实测。**
3. **固件下载后的两处延时只有 10 ms**（中危，审计时判断）——审计当时只对照了 `rtl-poe.c` 的 50ms；修复轮补齐 ko 与 rtlgsw 两侧证据后**推翻该判断**，详见下文 C2 更正。

## 1. 前序分析文档核对结果

### 1.1 确认无误（本次补充了更强的证据）

| 结论 | 新证据 |

### 1.2 发现错误 / 需要更正的分析结论

**D1【结论错误】`RTL8238B_POE_寄存器映射与协议.md` §7 —— 已修复**

> 原文：「`rtl8373n.ko` 的 `rtl8238b_probe` 仅做使能/初始化（0xEC/0x1A/0x12/0x01），反汇编中**未出现 `0xF4` 流式写**……真正的固件流式下载由用户态 `rtlgsw` 在启动时完成。」

**实际相反。** ko 的 probe 自己完成完整下载：0x2a0 起就是「按 `ids[k]` 选镜像 → 调 `pse_8238_i2c_write_buf.constprop.0` → `udelay` → k++」的循环，而 `pse_8238_i2c_write_buf` 的第一条指令就是 `strb w3(0xF4), [x0], #1`。内核侧的批量写函数是 `pse_8238_i2c_write_buf.constprop.0.isra.0`（符号表可查）。

这个错误有实际影响：它让人以为「用户态只需要检测、不需要下载」，而我的实现选择了自己下载——这个选择是对的，但理由和文档写的不一样。

**D2【证据不足，标注过强】§4 寄存器总表中的 `0x1E` —— 已修复**

> 原文：「`0x1E` W/R PORT_LIMIT? 端口功率限制/分类（观察为寄存器参数）……【已确认存在】rtlgsw `mov w19,#0x1e`（0x40c3cc）」

核查结果：rtlgsw 里所有 `#0x1e` 立即数都不是寄存器地址。
- `0x40c3cc: mov w19,#0x1e` 位于 `cmp w19,#0x9; b.hi 0x40c344` 的端口索引查表路径里（表在 `0x459000+1904`），`0x1e`(30) 是**默认值/位索引**，不是寄存器号。
- `0x40d410` 等处的 `mov w1,#0x1e` 是调 `0x40ccc0(w0=slot, w1=bit, w2=onoff)`，而 `0x40ccc0` 内部是 `ldr w0,[sp,#76]` → `lsl w1,#1,w21` → `bic/orr csel` 的**软件位图 set/clear**，与 I2C 无关。

建议把 `0x1E` 从【已确认存在】降级为【未确认】，或直接删掉——实现里没有用它，且厂商的 init 路径也不写它，这一降级不影响代码，但能避免后续照着这个"寄存器"去写无效代码。

**D3【标注过时】§4 的 `0x01` —— 已修复**

原文标为【推断】。实际上 ko 的 probe 在 0x3ac–0x3c4 明确写 `0x01 = 0x00`（`strh w24(1), [sp,#110]` 作寄存器号，`strh wzr` 把值字节清零，`len=2`）。应升级为【已确认】。

## 2. 代码审计结果

### C1【高危 · 功能性】`write_bulk` 的固件流格式与厂商不一致 —— **已修复**

`src/main.c` 当前实现：

```c
while (offset < len) {
        buffer[0] = reg;                 /* 每条都带 0xF4 */
        memcpy(buffer + 1, data + offset, chunk);
        msg.len = chunk + 1;
        ret = transfer(bus, &msg, 1, false);   /* 独立 transfer，块间有 STOP，无 flags */
        ...
}
```

厂商 rtlgsw 的 `0x40bbcc` 实际做法（反汇编 0x40bc80–0x40bdd8 解码）：

| | 载荷 | flags | `0xF4` 前缀 | 发送方式 |
|---|---|---|---|---|
| 第 1 条 | ≤ 8191 | `0x1000` = `I2C_M_IGNORE_NAK` | **有** | 全部消息合并为**一次** `I2C_RDWR` |
| 第 2..n 条 | ≤ 8192 | `0x5000` = `I2C_M_IGNORE_NAK\|I2C_M_NOSTART` | **无** | 同上 |

三处差异，任一条都可能导致镜像损坏：

1. **`0xF4` 被重复注入**。芯片收到第一个 `0xF4` 后进入流式接收，我后续块里的 `0xF4` 会被当作固件数据字节吞掉 → 镜像错位 → `0xEC` bit5 永不置位。
2. **块间是 STOP 而不是 repeated start**。厂商专门给后续消息设 `I2C_M_NOSTART`，说明这颗芯片的加载引擎要求一次连续传输；我用独立 transfer，每条之间都有 STOP。
3. **缺少 `I2C_M_IGNORE_NAK`**。厂商第一条就设了这个 flag。

失败模式是**响亮的**（bit5 校验不过 → `-EIO` → 守护进程退出并打日志），不会静默写错功率，但功能是死的。

**为什么这条特别值得担心**：原厂 `etc/init.d/rtlgsw` 第一件事就是 `rmmod rtl8373n`，再 `modprobe bm_gsw`，然后起 `/usr/bin/rtlgsw -f`。也就是说原厂体系里 **PSE 完全由用户态接管**，固件下载正是 `rtlgsw` 用上面那套分块 + NOSTART 的格式做的。我的守护进程就是 `rtlgsw` 的替代者，这条路径不是备用路径，是主路径。

顺带一个反向印证：`pse_src/rtl-poe.c` 里的 `pse_reg_write_buf` 是一次性 `malloc(len+1)` 单条消息——那个写法在用户态会被 i2c-dev 的 8192 限制直接 `EINVAL` 拒掉，21164 字节的大固件根本下不去。所以"必须分块"是对的，但**分块的格式要对齐厂商**，不能只对齐字节数。

### C2【中危 · 时序】固件下载的两处延时偏短 —— **修复轮已推翻，维持 10ms**

审计当时的判断依据是「`rtl-poe.c` 两处都是 `usleep(50000)`」。修复轮补齐证据后发现该依据不成立：

1. **`rtl-poe.c` 不是原厂代码**，是本项目早期的分析稿/原型（文件头自述 "luci-app-rtl-poe … 寄存器映射从原厂固件反汇编得到"），其单条 21165 B 消息的写法在任何带 8192 限制的内核上都会被 `EINVAL` 拒掉，说明它未在真机跑通过，其延时时值没有权威性。
2. **ko 的 probe 用 ~10ms**：两处延时均为 10 次 `__const_udelay(0x418958)`。arm64 `__udelay(us) = __const_udelay(us * 0x10c7)`（`arch/arm64/lib/delay.c`），而 `1000 × 0x10c7 = 0x418ce8`，与 `0x418958` 仅差 0.03% ⇒ 每次迭代 ≈ 1ms，10 次 ≈ **10ms**。
3. **rtlgsw 用 10ms**：`0x1A=0x3F` 后 `delay_ms(10)`（0x408688）、镜像写完后 `delay_ms(10)`（0x4086e4）、init 两个 `0x12` 之间也是 `delay_ms(10)`（0x40877c/0x4087b4）。

两个真机在跑的产物（ko + rtlgsw）一致给出 ~10ms，**代码维持 10ms 并在三处延时加了证据注释**。若上板发现下载不稳，再按 50ms 放宽（单行改动）。

### C3【中危 · 输入级矛盾】端口数与端口映射有两套互相矛盾的说法

这是本次审计发现的**最大的未决问题**，代码目前静默选了其中一套：

| 来源 | 说法 |
|---|---|
| `pse_src/README.md` / `rtl-poe.c` | **7 个 PoE 口**：LAN7=端口0 … LAN1=端口6；端口 0–3 在 0x20，端口 4–6 在 0x21 |
| `pse_src/RTL8238B_POE_Web界面功能.md` §5 | **8 个 PoE 通道**：Web 命名为 **WAN、LAN2、LAN3、LAN4、LAN5、LAN6、LAN7、LAN8**，与 `pseinfo` 的 `pse1–pse8` 一一对应；推断 LAN1 是上联/非 PoE 口 |
| `etc/config/pseinfo` | `pse1–pse8` 共 8 节，`pse1 enable='0'`（默认关闭），`pse2–pse8 enable='1'`；`allow '1111111'` 每节 7 位 |

Web 文档自己把这一点列成了「与前期 README 的差异」并标为待确认，但**代码把它当已决事实处理了**：

```c
{ RTL8238B_COMPATIBLE, "RTL8238B", RTL8238B_I2C_NODE, 0x20, 2, 8, 7, 90000,
  false, { 7, 6, 5, 4, 3, 2, 1 }, &tmi_chip_rtl8238b },
```

- `ports = 7` 且 `port_map = {7,6,5,4,3,2,1}` —— 采用 README 的 7 口反序映射
- 若 Web 文档的说法成立，映射应是**恒等**的（通道 1–7 = LAN2–LAN8，通道 0 = WAN），端口数也应改为 8

影响面：LuCI 页面行数与命名（现在显示 LAN1–LAN7，原厂显示 WAN + LAN2–LAN8）、`tmi_board_mask`、日志里的 LAN 编号、以及关错口的风险。**这一条建议在真机上用「关一个口看哪个网口掉电」实测后再定**，不建议继续靠文档推断。

> **处理决议（2026-10-19 晚）**：用户明确 C3 保留现状、上板实测后再定修改方向。代码未动映射，板表注释已改为显式说明「7 口反序 vs 8 通道两套输入矛盾、以实测为准」，`overview.js` 暂不改。

### C4【低危 · 注释矛盾】`src/tmi.c` 板表注释 —— **已修复**

```c
/* Channel 7 is not wired on this board, so LAN1..LAN7 use channels 7..1. */
{ ... { 7, 6, 5, 4, 3, 2, 1 } ... }
```

前半句若按 0-based 理解（未用的是 index 7）是对的，后半句 `port_map` 是 1-based 通道号，两句混用了两套编号。按 1-based 说法未用的应是第 8 通道。读者很容易误以为 LAN1 没接线。建议统一成「`port_map` 存 1-based 通道号；未接线的是 index 7（1-based 第 8 通道）」。

已改为：显式声明 `port_map` 为 1-based、未用的是第 8 通道、并注明与 Web 逆向的矛盾待实测；`tmi.h` 的 `port_map` 字段注释同步为「port index (LAN1 first) -> one-based PSE channel」。

### C5【低危 · 死代码】`struct transport.address` —— **已删除**

重构后 I2C 地址改为逐调用传入（`read_reg`/`write_reg`/`write_bulk` 都带 `address` 参数，`i2c_msg.addr` 逐消息设置），`bus->address` 已无人读写。留着容易让人以为还有个全局地址。

字段定义与 `main()` 里的 `bus.address = board->address;` 赋值均已移除，编译无警告。

### C6【低危 · 输出可读性】RTL8238B 的文本状态输出 —— **已修复**

`print_status` 非 debug 分支会打印 `voltage-mv=0` 和 `current-ma=0`——这两个字段对 RTL8238B 是**故意置 0** 的（标度未公开，只发布 mW）。打印 0 会被误读成"实测 0V/0A"。建议与 `input_mv` 的处理保持一致，输出 `unavailable`。

实现方式：`struct tmi_chip` 新增能力标志 `analog_scaled`（TMI=true，RTL8238B=false），`print_status` 据此输出 `voltage-mv=unavailable / current-ma=unavailable / power-mw=N`。宿主测试断言：RTL8238B 不再出现 `voltage-mv=0`，TMI 仍输出 `voltage-mv=53000 / current-ma=500 / power-mw=26500`，JSON schema 不变。

## 3. 复核通过、未发现问题的项

为避免重复劳动，以下都逐条核对过，**结论是可保持现状**：

- **传输层双地址路由正确**：`read_reg`/`write_reg`/`write_bulk` 都用 `i2c_msg.addr = address`，不依赖 `I2C_SLAVE`，0x20/0x21 分流没问题。
- **`open_bus` 的 `fd` 初值 bug 已修掉**（上一轮发现的 `-ENODEV` 误判），当前逻辑正确。
- **`channel_location()` 与 `port_ctrl_byte()` 的通道→设备/位偏移换算**，与 `rtl-poe.c` 的 `port_to_reg()` 逐位一致（在 7 口假设下）。
- **`check_policy_status` 比对 `0x12` 整个字节**（含未用通道的 bit 6-7）不会误报——因为 `rtl8238b_initialize` 里的 `write_port_mask` 会把这两个位清零，之后芯片读回的值与期望值一致。
- **`modes[2]` 容量**对三块板都够（`channels/4` 最大为 2）。
- **`protocol` JSON 字段不是回归**：对比 `git show HEAD:` 的原始 `main.c`，原本就是 `powered && good → "unconfirmed"`，TMI 侧也一样，行为未变。
- **`print_status` 改用 `power_mw[port]`** 对 TMI 数值等价（原式为 `voltage_mv*current_ma/1000`，`tmi_read_snapshot` 里就是这么算的）。
- **`input_valid` 门控、`hardware_budget` 分流、复位 GPIO 可选化**三处语义正确，没有把 TMI 的假设泄漏到 RTL8238B。
- **日志叙述对 RTL8238B 合理**：`detect/classify` 填使能掩码使 `automatic` 为真，从而输出"waiting for a valid PoE device"而不是误报"automatic PoE detection is not active"；`events[]` 全 0 所以不会刷故障/ supply 事件。
- **固件 blob 未被意外改动**：与 `pse_src/rtl8238b_fw.h` 数组部分字节级一致，只换了头注释；且新注释里"提取自 rtl8373n.ko"的说法经实测成立（反而是原 `pse_src` 注释里"提取自 kernel.vmlinux"不够准确）。
- **`get_board()` 多字符串解析无越界**。
- **编译与测试**：`gcc -Wall -Wextra -Werror -O2` 通过；RTL8238B 与 TMI 两套寄存器模型测试全绿。

## 4. 部署面新发现（影响落地方式）

**E1 原厂把 PSE 完全交给用户态。** `etc/init.d/rtlgsw`：

```sh
if [ -n "$(lsmod | grep rtl8373n)" ]; then rmmod rtl8373n; fi
modprobe bm_gsw
procd_set_param command "$PROG" -f
```

两个推论：
- **好消息**：`rtl8373n.ko` 被主动卸载，不会在 0x20/0x21 上绑定驱动，所以 `open_bus` 的 `I2C_SLAVE` 不会撞 `EBUSY`，"尊重内核驱动所有权"的设计不会把自己挡在门外。
- **坏消息**：正如 C1 所述，我的守护进程直接顶替 `rtlgsw` 的职责，固件流格式必须对齐。

**E2 `realtek,rtl8238b` 是 PSE 设备节点的 compatible，不是板级 compatible。** `objdump -s -j .rodata rtl8373n.ko` 显示 `rtl8238b_dt_ids` 内容是 `"realtek,rtl8238b"`，`rtl8238b_i2c_ids` 同源。所以板级 DTS 里需要的是一个 `i2c@...` 下的子节点 `compatible = "realtek,rtl8238b"; reg = <0x20>;`。当前 `tmi.c` 里 `RTL8238B_COMPATIBLE "beecon,beeconmini2"` 是**板级** compatible（用于 `get_board()` 匹配 `/sys/firmware/devicetree/base/compatible`），两者不是一回事，替换时不要混。

**E3 `pseinfo` 的 `sys.warn_threshold '90'`** 与实现里 `max_budget_mw = 90000` 吻合，90W 这个取值有原厂配置佐证。

## 4.1 修复轮补充查证（为 C1/C2 取证时的新发现）

**N1 原厂内核是 6.12.74（主线版），这直接验证了 C1 的修复方向。** `modinfo vermagic` = `6.12.74 SMP mod_unload aarch64`；DWARF 显示由 `linux-mediatek_filogic` 目标构建（与本 ImmortalWrt 树同目标族）。主线 6.12 的 `i2c-mt65xx.c` **不处理 `I2C_M_NOSTART`**（grep 零命中），也就是说 rtlgsw 在原厂真机上跑时，续传消息的从地址本来就会被重复发送——而它是出厂在用的守护进程。**结论：芯片的 I2C 地址匹配器会消费流中的重复地址字节，`write_bulk` 按 rtlgsw 格式实现即可，不需要（也没有）更"无缝"的用户态途径。**

**N2 `i2c-dev` 的两条路径都走不通大消息。** 主线 `drivers/i2c/i2c-dev.c`：`I2C_RDWR` 对单条 `len > 8192` 返回 `-EINVAL`；`read/write` 路径则是 `if (count > 8192) count = 8192;` **静默截断**。所以 rtl-poe.c 的单条 21165 B 消息必败，分块是唯一选择——但格式必须对齐厂商（C1）。

**N3 文档还有两处错误（审计时未覆盖，取证时发现，已一并修正）：**

- **§1「RTL8238B 通过 RTL8373N 内置 I2C 主控制器（I2C_MST1）间接访问」不成立。** ko 的 `pse_8238_i2c_read/write/_write_buf` 全部调用标准 `i2c_transfer()`，从地址取 `client->addr`、适配器取 `client->adapter`（DWARF + 反汇编对照 `struct i2c_client` 布局：+0=flags、+2=addr、+24=adapter，均与 6.12 主线一致）；ko 只 `i2c_register_driver`，从无 `i2c_add_adapter`。RTL8238B 就在 SoC I2C 总线（= rtlgsw 用的 `/dev/i2c-0`）上，I2C_MST1 符号属于交换机驱动自身。
- **§3「ko 自定义 flags = 0x10000/0x10001」是误读。** 那是 `pse_8238_i2c_read` 里 `stur w7(0x10000),[sp,#66]` / `stur w5(0x10001),[sp,#82]` 的 **(flags,len) 打包 32 位存储**：实际 flags 为 0x0000（写）与 0x0001（`I2C_M_RD`），全是标准值。写 helper 的 flags 是 `client->flags & I2C_CLIENT_TEN(0x10)`，7-bit 设备即 0。

**N4 DWARF 其他有用信息**：ko 源文件为 `rtlgsw.c` / `rtl8238b.c` / `rtl8373_mdio.c` / `chip.c` / `rtk_switch.c` / `identify.c` / `dal/*`（OpenWrt 包 `switch-rtl8373n`）；`pse_image_RTL8238B_bin`（21164 B）在 VA 2050、`pse_image_RTL8238C_bin`（8028 B）在 VA 240；`rtl8238b_probe` 位于 `rtl8238b.c:1987`，`pse_8238_i2c_write_buf` 签名 `(client, addr, buf, size, exaddr)` 位于 `rtl8238b.c:1892`。

**N5 C1 的残余风险（需上板确认）**：主线 mtk 驱动把多消息传输逐条交易（消息间 repeated start + 重发地址）。只要芯片地址匹配器正常消费这些字节（N1 的证据表明如此），下载即可完成；若真机出现 bit5 校验失败，下一个嫌疑就是这一点，届时只能走内核模块方案。

## 6. 一句话结论

协议层（寄存器、公式、镜像选择、双设备）的逆向是可靠的，固件 blob 也验证无误；**主要风险集中在"用户态固件下载的报文格式"和"端口映射的输入源矛盾"这两点**。前者已按厂商反汇编重写并通过逐字段测试，且原厂内核同为 6.12（NOSTART 不被支持）这一事实反向证明芯片容忍流中重复地址；后者按决议保留，待真机实测。其余注释、死代码、文档标注与输出可读性问题均已修复。
